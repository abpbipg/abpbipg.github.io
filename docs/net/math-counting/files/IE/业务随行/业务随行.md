传统园区的准入认证缺陷
1、认证策略点设备，需要部署大量的 ACL、VLAN 及 DHCP 地址池

2、设备的认证点和策略点必须相同一台设备，否则就需要通过策略联动来实现访问控制
	补充：认证点可以得知用户认证成功后分配的 VLAN 和 ACL 信息
		  但是认证的策略点不清楚用户认证后获取的信息，所以就必须认证点和策略点都是同一台设备

	*解决方法：认证点和策略点建立 CAPWAP 隧道，使用策略联动来进行感知
		           认证点可以把授权信息通过隧道转发给策略执行点

3、传统园区设备都是分布式架构的
     	补充：每台设备都有自己的路由表、转发表和 ACL、VLAN 等规则
	（例如：LSW1 配置了 ACL 3000，但是交换机 LSW2 不会进行同步，如果希望 LSW2 执行相同的 ACL 3000 策略，就必须登录 LSW2 完成配置）
	配置量大，且不易于修改（不易于管理）


一、业务随行概念
1、安全组（ucl-group）
	是指一类设备的集合（如：PC、手机、摄像头、网络设备等）
	① 静态添加
		ucl-group name OA					// 创建安全组
		ucl-group ip  10.1.1.0  24  name OA		// 把 10.1.1.0/24 网段加入到安全组 OA 中

		静态组的 IP 地址是固定的，根据配置生效（如：10.1.1.0/24 属于 OA 的安全组）

	② 动态安全组
		用户和授权结果进行绑定
		如：创建用户：zs 密码：Huawei@123
		       授权结果，安全组 ucl-group OA

		当 zs 用户认证成功后，自动划入安全组 OA 中
		动态安全组于 IP 地址无法，用户认证成功后会分配一个组 ID，根据组 ID 划入相应的安全组（IP 地址不固定）

	补充：如果同时配置，则动态安全组优于静态安全组

	特殊的安全组
	① unknown 组：没有通过静态安全组或动态安全组分类的用户，自动划入 unknown 组
				（缺省组）
	② any 组：代表所有能够访问的资源集合，只能作为目的组（无法成为源组）	
			（缺省组）

	③ 逃生组：IP-Group 推送失败后，用户无法得知进入哪个安全组，则可以划分到对应的逃生组
			（需要手工指定，非缺省配置）


2、资源组
	背景：服务器 192.168.1.100/32 既是 HTTP 服务器，也是 FTP 服务器
		   那么如果使用静态安全组配置，如下：
			ucl-group name Server						// 创建静态安全组
			ucl-group ip  192.168.1.100  32   name Server	

		如果 OA 用户，可以访问 HTTP 服务器，但是禁止访问 FTP 服务器，无法使用安全组来进行区分
		（因为 IP 地址一致，设备无法根据安全组来区分，补充：安全组无法添加端口号）

	需要区分相同 IP 地址但不同服务资源的情况，则可以使用资源组进行划分
	资源组允许 IP 地址相同，但服务类型不同的服务器
	——————————————————————————————————————————————————
	如：资源组
		192.168.1.100 DNS
		192.168.1.100 HTTP    划分两个不同的资源组

	（资源组不能作为源组，只能作为目的组）


3、策略矩阵（组间策略）
	不同的安全组和资源组，需要通过策略矩阵来控制是否可以访问
	策略矩阵可以通过用户的意图，由 iMaster 自动下发 ACL

	如：acl 9999
	       rule 10 permit ip source ucl-group name OA destination 192.168.1.0 0.0.0.255		允许 OA 组成员访问，192.168.1.0/24 网段
	       rule 20 deny ip source ucl-group name OA destination ucl-group name RD		拒绝 OA 组成员访问 RD 组成员


4、IP-Group 表项订阅
	当认证点和策略点设备不是同一台设备是，需要配置 IP-Group 订阅和推送，使得设备能够获取用户的认证和安全组信息
	类似于传统 NAC 的策略联动
